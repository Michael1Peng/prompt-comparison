# 项目简报：提示词扫描CLI工具

**会议日期：** 2025-09-13  
**项目分析师：** Mary  
**项目状态：** 准备开始开发  

## 执行摘要

**提示词扫描CLI工具** - 一个简单的命令行脚本，用于在代码库中找到并提取AI提示词文本。

**解决什么问题：** 开发者想快速查看其他项目是如何编写提示词的，但手动搜索太慢。

**工具功能：** 扫描文件夹，输出一个包含所有找到的提示词的JSON文件。

**目标用户：** 正在学习提示词写法的开发者。

## 问题陈述

**当前状况：** 开发者在学习和改进提示词写法时，经常需要查看优秀开源项目中的提示词实例。然而，提示词内容分散在各种文件中（.md、.txt、.js、.py等），格式和位置都不统一。

**痛点影响：**
- 手动搜索提示词耗时费力，一个中等规模的项目可能需要30-60分钟
- 容易遗漏隐藏在代码注释或配置文件中的优秀提示词案例
- 无法快速对比同一项目中不同场景的提示词设计

**现有方案不足：** 
- 文本搜索工具（grep, ripgrep）需要提前知道搜索关键词，容易遗漏
- IDE搜索功能同样依赖关键词，无法智能识别提示词内容
- 缺乏专门针对提示词内容识别的工具

**解决的紧迫性：** 随着AI应用快速发展，提示词工程技能日益重要，开发者迫切需要高效的学习工具来快速积累提示词设计经验。

## 解决方案描述

**核心方案：** 开发一个 Node.js CLI 工具，通过以下三步流程自动发现和提取提示词：

1. **智能预筛选** - 扫描指定目录，识别可能包含文本内容的文件类型（.md、.txt、.js、.py、.yaml、.json 等）
2. **AI 识别** - 调用 Qwen 模型判断文件是否包含提示词内容，并提取具体的提示词文本
3. **结构化输出** - 将发现的提示词保存为 JSON 格式，包含内容、文件位置、行号等基本信息

**核心差异化优势：**
- **AI 驱动识别**：不依赖关键词搜索，能智能理解什么是提示词内容
- **一键操作**：简单的 `npm run scan` 命令即可扫描整个项目
- **标准化输出**：统一的 JSON 格式便于后续处理和分析

**为什么会成功：** 
- 解决了手动搜索效率低下的核心痛点
- 技术栈简单可靠（Node.js + 成熟的 AI API）
- 输出格式标准化，易于集成到其他工具链中

**产品愿景：** 成为开发者学习提示词设计时的标准辅助工具，就像 `eslint` 对代码质量检查一样便捷。

## 技术考虑

### 平台要求
- **目标平台：** Node.js 18+ (跨平台支持)
- **运行环境：** 命令行终端，支持 Windows/macOS/Linux
- **性能要求：** 50-100个文件项目扫描时间 < 3分钟

### 技术偏好
- **前端：** 无（纯CLI工具）
- **后端：** Node.js + 标准库（fs、path）
- **数据库：** 无（直接输出JSON文件）
- **AI集成：** Qwen API（HTTP调用）
- **依赖管理：** npm，最小化外部依赖

### 架构考虑
- **代码结构：** 单文件脚本（scan.js），避免复杂的模块分割
- **服务架构：** 无服务架构，本地运行
- **集成需求：** 
  - Qwen API密钥配置（环境变量）
  - 标准JSON输出格式
- **安全/合规：** 
  - API密钥本地存储
  - 不上传用户代码内容
  - 只读文件系统访问

## 风险与开放问题

### 关键风险
- **API依赖风险**：Qwen API服务不稳定或调用失败可能导致工具完全无法工作
- **识别准确率风险**：AI模型可能无法准确区分提示词和普通文本，产生大量误报或漏报
- **性能风险**：大型项目扫描可能超过3分钟时间限制，影响用户体验
- **开发时间风险**：2小时时间窗口可能不足以完成基本功能和调试

### 开放问题
- 如何定义"提示词"的边界？代码注释中的AI相关内容是否算提示词？
- JSON输出的具体字段结构是否满足用户的实际使用需求？
- 是否需要支持中文提示词的识别？
- 遇到API调用失败时，工具应该如何表现？继续还是停止？

### 需要进一步研究的领域
- 不同类型开源项目中提示词的分布模式和常见位置
- Qwen API在提示词识别任务上的实际表现基准
- 竞争工具或类似解决方案的用户体验设计
